# 工人控制度改造方案与土地／生产资料所有权饼图设计

> 本文是[游戏设计文档](../游戏设计文档.md) §12「工会与生产控制」与[经济改造方案](./经济改造方案.md) §16 的正式设计定稿。
> 决策对象：`stats.workerControl`（工人控制程度，0—100 单一标尺）由**两张六分饼**取代：
> **土地所有权**（教会土地／大庄园／中小地主与自耕农／农业合作社／农业集体／国有土地）与
> **生产资料所有权**（外资控制／大资本私有／小业主私有／工业合作社／地方工会所有／国有制）。
> 本文只写设计定稿与迁移方案；所有字段名、初值、公式、阈值都可直接落笔。
>
> **第 2 版变更**：分份从"工会／国家／私人"三分改为用户指定的**六分模型**，并采用用户给定、已核对和恒为 100 的三份剧本初值（§2.4）。
> **第 3 版变更**：1933·11 的生产资料初值按用户修订更新为 `外资 10 / 大资本 39 / 小业主 44 / 工业合作社 3 / 地方工会 1 / 国有 3`；随之补上 `transferControlShare` 的**出方容量不足处理**（1933 的外资只有 10，而"没收外资"每次要 −6）与 §2.4／§4.2 的相应结论。
> **第 4 版变更**：**第 5A 期（数据与规则）已实施完成**，见 §10。实施中发现并修正了三件事：① **"与旧数值逐月一致"这条验收标准不成立**，改用三条可证伪的不变量（§10.2）；② 月度收拢的按比例削减会被整数化抹掉，改成"削减量记到最大的社会化桶"；③ 五月事件的门槛必须**立刻**改读所有权数据，否则手写状态的测试夹具会读到过期的派生缓存值。
> **第 5 版变更**：**第 5B 期（内容层换口径）已实施完成**，见 §10.5。五月事件按用户定稿改为**两道门槛**——CNT 工会占比 ≥30 **且** 工业地方工会所有制 ≥25（§5.2），并在事件界面显示两项读数；两条经济路线的控制权门槛改成形状相反的两个命名判定（§5.1）。
> **第 6 版变更**：**第 5C 期（土地集体化日志 + 界面）已实施完成**，见 §10.7。四件事：① 土地集体化日志落地，**完成条件读土地饼的集体份额 ≥65%**（不是计数器），开始事件按经济改造方案 §13 要求"土改过半 + 已投过一次集体化"；② 侧边栏的旧"生产资料控制"条换成**两张六分饼**（上下依次排列、不并排，配色按用户指定）；③ §4.4 的双写问题以"**向量声明在计数器上**"落地（§4.6），27 个调用点改写并加源码级守卫；④ 沙盒的 12 个所有权滑杆取代已失效的 `workerControl` 滑杆（它早已被 `postReducer` 覆盖，拉不动的）。另外记一次**数据事故**：两个动作卡文件与两处计时器声明被误删，已按构建产物重建（§10.6）。
> **第 7 版变更（当前）**：**效果归属按用户定稿回到"选项引发效果"**，见 §10.8。`applyEconomicOption` 恢复为"**选项自带向量 + 计数器 +1**"，**删除 `ECONOMY_COUNTER_TRANSFERS`**（§4.3／§4.4／§4.6 已重写）；**军事类选项不再写经济效果／经济计数器**（五月事件、民兵合法性、战时权力安排、军事化抉择）；**经济日志（六条路线 + 土地集体化）删除月度 `activeEffect`**。宏观换算仍处于暂停状态。

## 0. 结论速览

| 项 | 决定 |
| --- | --- |
| 单一标尺 `stats.workerControl` | 拆成**两张六分饼**，取代一根 0—100 的条 |
| 每张饼的分份 | 土地 6 份、生产资料 6 份；**和恒为 100**（整数百分比，与 `unionShare` 同一量纲） |
| 落点 | `GameState.controlShares: { land, industry }`；**不进 `stats`** |
| 初值 | 按剧本显式声明（§2.4，即用户给定的三组数据），进 `SCENARIO_OWNED_KEYS` |
| 唯一写入口 | `transferControlShare(state, sector, delta)` —— **整张饼的增量向量一次配平**，天然守恒 |
| 月度漂移 | "战前封顶 40"改为**两条结构性上限**：社会化总量（合作社+集体/地方工会+国有）逐月朝上限靠拢 |
| 迁移 | **两阶段**：5A 并行（`workerControl` 降级为派生值，15 个写入点一行不改）→ 5B 逐点换口径 |
| 三个派生指标 | `unionShare`（工会）／`socializedShare`（社会化）／`privateShare`（私人），三者恒为 100 |

**这套模型相对三分模型的实质改进**：它把"私人"拆成了**教会土地／大庄园／中小地主与自耕农**（土地）与**外资／大资本／小业主**（生产资料）。这不是数量上的细化，而是**政治上的必需**——因为 CNT 的土地政策对这三种人的态度完全不同：

- **大庄园与教会土地**是没收对象（`land_requisition` 直接吃这两项）；
- **中小地主与自耕农**是**必须争取、不能得罪**的对象（`land_redemption` 与 `agricultural_cooperative` 只动这一项，且给的是自愿入社）；
- **外资控制**是民族主义与国际关系的交汇点（`foreign_capital_seizure`、`wartime_trade_monopoly`）；
- **小业主私有制**是城市里的自耕农等价物（`industrial_cooperative` 的对象）。

三分饼只能表达"私人还剩多少"，六分饼能表达"**我们在动谁**"——而这正是 1930 年代西班牙农村政治的全部内容。

### 1.4 单标尺的三个结构性问题

1. **城乡不可分**：`land_and_freedom` 的农业集体化与佩罗的工业集体化加的是同一个数字，"阿拉贡的村庄集体化了"与"巴塞罗那的工厂被接管了"在数据上完全等价；
2. **没有对手方**：0—100 没说清剩下的归谁。现实里是三足鼎立——CNT 工会与集体、共和国国家、以及**教会／大庄园／外资／大资本／小业主**这一整片私人世界；
3. **只能涨，且"收回"读不出来**：1937 年五月事件之后国家与共产党把集体化工厂收回去，在单标尺里只能写成"工人控制 −12"，读起来像凭空蒸发。

## 2. 数据模型

### 2.1 字段

```ts
/** 土地所有权的六种归属（docs/工人控制度改造方案.md §2）。 */
export type LandOwnershipKey =
  | 'church'        // 教会土地
  | 'latifundia'    // 大庄园所有制
  | 'smallholders'  // 中小地主与自耕农所有制
  | 'cooperative'   // 农业合作社
  | 'collective'    // 农业集体
  | 'state';        // 国有土地

/** 生产资料所有权的六种归属。 */
export type IndustryOwnershipKey =
  | 'foreign'       // 外资控制
  | 'bigCapital'    // 大资本私有制
  | 'smallBusiness' // 小业主私有制
  | 'cooperative'   // 工业合作社
  | 'union'         // 地方工会所有制
  | 'state';        // 国有制

export type LandOwnership = Record<LandOwnershipKey, number>;
export type IndustryOwnership = Record<IndustryOwnershipKey, number>;

/** 两张所有权饼。每张六份，和恒为 100。 */
export interface EconomyOwnershipShares {
  land: LandOwnership;
  industry: IndustryOwnership;
}
```

放在 `GameState` 顶层（**不进 `stats`**）：

```ts
  /**
   * 土地与生产资料所有权份额（两张六分饼，各张和恒为 100）。
   * 取代 `stats.workerControl` 的单标尺；唯一写入口是 `transferControlShare()`。
   * 单位是整数百分比，与 `unionShare`、`classes.support` 同一量纲。
   */
  controlShares?: EconomyOwnershipShares;
```

**为什么 optional**：与 `unionShare` 同理——旧存档没有该字段时由 `migrateControlShares` 按剧本初值补齐；运行期由 `getControlShares(state)` 兜底，调用方不需要判空。

**为什么不放进 `stats`**：`stats` 里现在全是"0—100 的单一标尺"（军队忠诚、紧张度、革命热情、官僚化…），通用代码（`war_effort_victory` 的路线效果、`mayDays` 的 `applyPolitics`）都假设"每一项就是一个百分比"。把两张六分饼塞进去会让这些通用代码对它做出错误假设（例如把整张饼当成一个可加减的标尺）。

### 2.2 三条不变量

1. **每张饼六份和恒为 100**，每份在 `[0, 100]`；
2. **唯一写入口** `transferControlShare(state, sector, delta)`：接受**整张饼的增量向量**并一次配平（§2.3），不允许逐个 bucket 手写增量；
3. **不允许并列写两套控制权数据**：饼落地后 `stats.workerControl` 只能是派生值或被删除（§3）。

### 2.3 唯一写入口：整张饼一次配平

六分饼的写入有一个三分饼没有的麻烦：一个行动往往要同时改好几个 bucket（"没收大庄园：集体 +2、合作社 +0.5、国有 +0.5，从大庄园 −2、教会 −1"），如果逐项 `adjustZeroSumShare`，后一次会覆盖前一次（第 2 期 `activateJournal()` 已经踩过同一个坑：每个补丁里都是整份对象）。

所以写入口接受**增量向量**并做一次归一化配平：

```ts
// src/game/rules/controlShares.ts

type Delta<S> = Partial<Record<keyof S, number>>;

/**
 * 把一张饼沿 `delta` 移动：正项按给定数额增加，负项按给定数额减少，
 * 未被指定的项按现有比例吸收差额，保证六项之和恒为 100、每项非负。
 *
 * 语义约定（§4.3）：一次行动只指定"进哪些桶、出哪些桶"，其余桶按现状吸收。
 *
 * **出方容量不足时的处理**（1933 剧本的外资只有 10，而 `foreign_capital_seizure`
 * 每次要求 −6、`rail_nationalization` 每次要求 −4）：先按可动用余额截断出方，
 * 再用"未指定的私人桶"按比例补足；**进方永远按承诺的数额足额到账**。
 * 这样"没收外资"在外资见底之后不会静默失败，而是转为没收国内大资本——
 * 这正是历史上外资撤走之后民族资本被盯上的顺序。
 */
export const transferControlShare = <S extends 'land' | 'industry'>(
  state: GameState,
  sector: S,
  delta: Delta<S extends 'land' ? LandOwnership : IndustryOwnership>,
): Partial<GameState> => {
  const current = getControlShares(state)[sector] as Record<string, number>;
  const next: Record<string, number> = { ...current };
  const explicit = new Set(Object.keys(delta));

  // 1. 进方足额到账；出方按可动用余额截断，并记下"还欠多少"。
  let promisedOut = 0;
  let actualOut = 0;
  for (const [key, value] of Object.entries(delta)) {
    if (!value) continue;
    if (value > 0) {
      next[key] = (next[key] ?? 0) + value;
      continue;
    }
    promisedOut += -value;
    const movable = Math.min(-value, Math.max(0, next[key] ?? 0));
    next[key] = (next[key] ?? 0) - movable;
    actualOut += movable;
  }

  // 2. 未被显式指定的桶按比例吸收"进方总额 − 出方实付"的差额。
  const moved = promisedOut - actualOut;   // 仍需要从隐式桶里补足的净额
  if (Math.abs(moved) > 1e-9) {
    const implicit = Object.keys(next).filter(key => !explicit.has(key));
    const pool = implicit.reduce((sum, key) => sum + Math.max(0, next[key]), 0);
    if (pool > 0) {
      implicit.forEach(key => {
        next[key] = Math.max(0, next[key] - moved * (Math.max(0, next[key]) / pool));
      });
    } else {
      // 全部桶都被显式指定：从当前最大的桶里扣，避免死锁。
      const largest = Object.keys(next).reduce((best, key) => (next[key] > next[best] ? key : best), Object.keys(next)[0]);
      next[largest] = Math.max(0, next[largest] - moved);
    }
  }

  // 3. 整数化并修正舍入：把误差记到最大的一项上，保证和恰为 100。
  const keys = Object.keys(next);
  keys.forEach(key => { next[key] = Math.round(next[key]); });
  const total = keys.reduce((sum, key) => sum + next[key], 0);
  if (total !== 100) {
    const largest = keys.reduce((best, key) => (next[key] > next[best] ? key : best), keys[0]);
    next[largest] = Math.max(0, next[largest] + (100 - total));
  }

  return { controlShares: { ...getControlShares(state), [sector]: next } } as Partial<GameState>;
};
```

**为什么必须一次配平**：`transferControlShare(state, 'land', { latifundia: -4, church: -1, collective: +4, state: +1 })` 是一句话，读起来就是"没收 4 点大庄园、1 点教会土地，转成 4 点集体、1 点国有"。分五次调用的写法既容易写错方向，也无法保证中间态守恒。

**取整与小数**：初值与转移向量都允许小数（§4.3 里 −0.5、+1.5 很常见），但**存进状态的一律是整数**（与 `unionShare` 一致，界面显示也不需要小数）。每次转移在最后一步四舍五入并把误差补到最大项，因此连续操作不会累积漂移。

**容量耗尽的观感**：1933 剧本里外资只有 10 点，
- 铁路国有化第 1 次消耗 4 点外资、第 2 次再耗 4 点（剩 2）、**第 3 次只有 2 点外资可动**，剩下 4 点转为从大资本出（`bigCapital` 被扣 2 + 隐式吸收 2）；
- 外资没收每次要 −6：第 1 次耗 6（剩 4）、第 2 次只能耗 4，其余 2 点从大资本出。

也就是说 **1933 剧本的"没收外资"在第二次就基本变成了"没收民族资本"**。这是设计上有意保留的反馈：外资池是有限的，而它见底之后玩家的行动会自动转向下一个目标。**界面上必须能看出这件事**（§6.2 的"与开局初值的差值"就是为此准备的）。

**已核对**（§0 的计算）：三组数据两张饼各自合计恰为 **100**，无需归一化。建议加一条启动断言，防止将来编辑数据时写坏：

```ts
const assertSharesSumTo100 = () => {
  Object.entries(INITIAL_CONTROL_SHARES).forEach(([scenarioId, shares]) => {
    (['land', 'industry'] as const).forEach((sector) => {
      const total = Object.values(shares[sector]).reduce((sum, value) => sum + value, 0);
      if (total !== 100) throw new Error(`INITIAL_CONTROL_SHARES.${scenarioId}.${sector} sums to ${total}, not 100`);
    });
  });
};
```

**这两组数据讲出来的故事（值得写进 UI 提示，也证明了六分模型的必要性）**：

| 观察 | 数据 | 含义 |
| --- | --- | --- |
| 教会土地三份剧本都是 **2** | `church: 2,2,2` | 教会的地没有被任何一届政府动过——它是那块"谁都不敢碰"的存量 |
| 1933 的土地变化全部在**大庄园 → 中小地主** | `latifundia 48→44`、`smallholders 44→46`，合作社 2→3，国有 4→5 | 1932 年的土地改革法**只动了闲置大地产**，两年只挪了 4 点，且其中有 2 点变成了自耕农的地——**这就是"温和土改"的全部成绩** |
| **工业的劳动者份额两年只从 2 涨到 4** | `cooperative 2→3`、`union 0→1` | 1931—1933 的工业产权变动几乎全是**私人内部的重组**，不是社会化。社会化的绝对量两次都一样（**7**），但结构完全不同——见下一行 |
| **社会化总量相同（都是 7），结构却反了过来** | 1931：合作社 2 / 工会 0 / **国有 5**；1933：合作社 3 / 工会 1 / **国有 3** | **这是六分饼最漂亮的一处证据**：三分饼（工会/国家/私人）会认为这两年"工业毫无变化"（社会化 7、私人 93），而六分饼看得见真实发生的事——**国有制退了两点，外资退了一半，小业主涨了七点**。共和国在紧缩与私有化，而外资在撤退 |
| 1936·5 外资**回到 18**，国有**回到 5** | 1933：`foreign 10, state 3` → 1936：`foreign 18, state 5` | 1934—1935 的右翼两年（勒鲁政府）把外资请了回来，国家也从危机里收回了一点资产。**三年里私人板块始终是 93 → 93 → 91**：共和、右翼、人民阵线三届政府都没能真正撼动工业产权 |
| 1936·5 土地的社会化 = 14、工业 = 9 | 土地 合作社 5 + 集体 1 + 国有 8；工业 合作社 3 + 工会 1 + 国有 5 | **乡村走在城市前面**——与 §4.2 的天花板设计（土地战前可达 21、工业最高 16）一致 |

> **这一版数据带来的一个重要设计后果**：工业的"私人板块"在 1931／1933／1936 分别是 93／93／91。也就是说**三份剧本的工业起点几乎一样**，玩家无论在哪个剧本开局，工业都要从零开始动。这是好事——1933 与 1936 的差异集中在**土地**（大庄园 48→44→40）与**政治配置**上，工业留给玩家去改变。剧本之间的手感差异因此不会因为"工业已经社会化了一部分"而被削弱。

### 2.5 派生指标（规则层唯一读出口）

```ts
// src/game/rules/controlShares.ts

export const getControlShares = (state: GameState): EconomyOwnershipShares =>
  state.controlShares ?? INITIAL_CONTROL_SHARES[state.scenario];

/** 某部门里"属于劳动者"的份额：合作社 + 集体 / 地方工会。**不含国有**。 */
export const getWorkersShare = (state: GameState, sector: 'land' | 'industry'): number => {
  const share = getControlShares(state)[sector];
  return sector === 'land'
    ? share.cooperative + share.collective
    : share.cooperative + share.union;
};

/** 某部门里"已脱离私人"的份额：工会份额 + 国有。 */
export const getSocializedShare = (state: GameState, sector: 'land' | 'industry'): number => {
  const share = getControlShares(state)[sector];
  return sector === 'land'
    ? share.cooperative + share.collective + share.state
    : share.cooperative + share.union + share.state;
};

/** 某部门里仍属私人（含教会与外资）的份额。三项派生值恒为 100。 */
export const getPrivateShare = (state: GameState, sector: 'land' | 'industry'): number => {
  const share = getControlShares(state)[sector];
  return sector === 'land'
    ? share.church + share.latifundia + share.smallholders
    : share.foreign + share.bigCapital + share.smallBusiness;
};

/**
 * 兼容读取器：**只统计工会份额**，不把国有算进"工人控制"。
 *
 * 这是本方案与新设计最容易被混淆的一点：国有化的工厂**不是**工人控制的工厂。
 * 旧口径的 `workerControl` 是"工人控制程度"，所以这里只取合作社 + 集体 + 地方工会。
 */
export const getWorkerControlEquivalent = (state: GameState): number =>
  (getWorkersShare(state, 'land') + getWorkersShare(state, 'industry')) / 2;
```

**三个派生值的关系**（`union + socialized + private` 不成立，因为 `union ⊆ socialized`）：

```text
private + socialized = 100
socialized = union + state   （"国有"与"合作社/集体/地方工会"是社会化内部的两条路）
```

## 4. 两张饼怎么动

### 4.1 转移的六个基本动作

十二个 bucket 之间的转移可以归纳成六个"动作原型"，所有内容（卡牌、顾问、事件、计数器）都用这六个原型表达：

| 原型 | 从 | 到 | 谁在用 |
| --- | --- | --- | --- |
| **没收** | 大庄园 + 教会土地 | 农业集体（+ 少量国有） | `land_requisition`、土地改革日志完成 |
| **赎买** | 大庄园 + 教会土地 | 国有土地（补偿登记） | `land_redemption` |
| **自愿入社** | 中小地主与自耕农 | 农业合作社 | `agricultural_cooperative`、`land_voluntary_collectivization` |
| **国有化** | 外资 + 大资本 | 国有制 | `rail_nationalization`、`foreign_capital_seizure`、`private_bank_seizure` |
| **工人接管** | 大资本 + 小业主 | 地方工会所有制 | `coal_nationalization`、加泰罗尼亚防御、国防委员会 |
| **小业主联合** | 小业主私有 | 工业合作社 | `industrial_cooperative` |

### 4.2 月度漂移：两条结构性上限

现行的 `controlObrero.ts` 做两件事：缺制度支撑时每月 −1，以及战前封顶 40。替换为**每张饼的社会化总量朝自己的结构性上限靠拢**：

```ts
export interface OwnershipCeilings {
  /** 社会化总量（合作社 + 集体 + 国有）的上限。 */
  land: number;
  /** 社会化总量（工业合作社 + 地方工会 + 国有）的上限。 */
  industry: number;
}

export const getControlCeilings = (state: GameState): OwnershipCeilings => {
  const unionRecognized = state.domesticPolicy.union_status >= 1;   // 结社自由
  const unionBargaining = state.domesticPolicy.union_status >= 2;   // 混合陪审团
  const landReformStarted = state.domesticPolicy.land_reform_progress >= 30;
  const war = state.civilWarStatus === 'ongoing' || Boolean(state.activeWar);

  if (war) {
    return { land: landReformStarted ? 92 : 45, industry: unionBargaining ? 95 : 55 };
  }
  return {
    // 农村可以走在城市前面：1932 年的卡萨斯·维耶哈斯与 1933 年的安达卢西亚农运
    // 已经证明乡村能先翻，但"没有土改就没有合法性"——进度不到 30 时只有 12。
    land: landReformStarted ? 21 : 12,
    // 城市被国家与老板一起压着：战前最高 16（结社自由 + 混合陪审团）。

};

/**
 * 月度收拢：社会化总量高于上限时，把超出部分按各项比例**退回私人三项**；
 * 低于上限时不动（上涨必须来自玩家的行动）。
 */
```

**三份剧本开局的位置**（用 §2.4 的初值算）：

| 剧本 | 土地社会化 / 上限 | 工业社会化 / 上限 | 是否已被上限压着 |
| --- | --- | --- | --- |
| 1931·4 | 6 / 12（未土改） | 7 / 10（`union_status` 1 → 结社自由） | 还有 3 点空间 |
| 1933·11 | 8 / 12（土改进度 0） | 7 / 16（`union_status` 2 → 混合陪审团） | 还有 9 点空间 |
| 1936·5 | 14 / 21（进度 0 但……） | 9 / 16 | 还有 7 点空间 |

> **三份剧本开局都在上限之下**，这是刻意的：旧设计里战前一律封顶 40，等于说"无论做了什么都一样"；新设计给了 3—9 点的腾挪空间，但也明确告诉你"战前别指望在城里翻盘"。注意 **1933 的工业社会化从 7 起（劳动者 4 + 国有 3），而不是 1931 的 7（劳动者 2 + 国有 5）**——上限相同、起点结构不同，玩家在 1933 剧本里推工会接管的起点比 1931 好一点。

### 4.4 效果属于选项，计数器只记账（用户定稿）

这一节换过三次写法，最终定稿是三条规则，**互相不替代**：

1. **效果由选项自己声明**（与其他选项写效果的方式完全一致）：动哪几个桶、动多少，
   写在选项的 `effect` 里，通过 `applyEconomicOption(state, counter, vector)` 或直接
   `transferControlShare()` 落地。
2. **计数器只记录"玩家做过几次这件事"**：它不携带向量、不按等级发奖、也不在月度结算里
   改动任何东西。单独调 `advanceEconomyCounter()` 必须对两张饼毫无影响
   （`test-control-shares.ts` 第 12 节①逐桶断言）。
3. **同一个计数器可以被两个选项推动，各写各的效果**：`land_and_freedom` 的「农业集体化」
   与 `agricultural_policy` 的「推广自愿集体化」都写 `land_voluntary_collectivization`，
   两个选项各自声明自己的向量——**效果属于行动，不属于计数器**。

> **两次走过的弯路，都记在这里，免得再走第三次。**
>
> - **第一次（第 3 期遗留）**：选项既写 `workerControl`（旧标尺）又写计数器，饼落地后
>   变成同一次点击转移两次；
> - **第二次（第 5C 期）**：把向量钉在计数器上（`ECONOMY_COUNTER_TRANSFERS`，一个计数器
>   一个向量），调用方一个参数都不传。它确实解决了双写，但代价是"计数器=效果"这个错觉，
>   也把两个选项推动同一计数器时的合理差异压平成一种口径。用户否掉了这个方向：
>   **要的是"选项引发效果，然后增加计数器"**。
>
> 现在 `ECONOMY_COUNTER_TRANSFERS` 已从 `rules/economyReforms.ts` 删除，只在本节留下记录。

**两条附则（同样是用户定稿）**：

- **军事类选项不写经济效果、也不写经济改造计数器**。五月事件的四种结算、民兵合法性的
  三个台阶、战时权力安排的三条路线、军事化抉择（民兵自治）都只结算政治：法律等级、
  派系异议、党派关系、战时联盟承诺度、革命热情与共和国权威。谁能拿到巴塞罗那的工厂
  由经济路线与生产关系行动决定，不由巷战结果决定。CI 里有源码级守卫：
  这四个文件里出现 `applyControlInfluence` / `applyEconomicOption` /
  `advanceEconomyCounter` / `transferControlShare` 任一，测试即失败。
- **经济日志不提供月度效果**（六条路线 + 土地集体化，共七本）。它们的 `activeEffect` 全部删除：
  路线的代价与收益只能来自行动、事件与它们各自写下的效果，日志本身只回答"这条路线走到哪一步了"。
  （此前五条路线各有月度修正，其中三条还是设计稿里有、代码里没有的"影子效果"；
  土地集体化日志原有的"雇农 +2/12、中农 −2/12 每月"也一并移除。）

### 4.6 计数器的边界（曾经的 `ECONOMY_COUNTER_TRANSFERS`）

5C 期一度存在一张 `ECONOMY_COUNTER_TRANSFERS` 表（18 条：计数器 → 转移向量），
`applyEconomicOption(state, counter)` 查表得到向量。它已被**删除**，理由是它在语义上把
"效果"和"记账"绑成了一件事，而用户要的是两件事：

| | 归属 | 写法 |
| --- | --- | --- |
| 效果（动哪几个桶、动多少） | **行动／选项** | `applyEconomicOption(s, 'land_requisition', { land: { latifundia: -2, ... } })` |
| 记账（做过几次） | **计数器** | 上面这一次调用里的 `+1`，或独立的 `advanceEconomyCounter()` |

因此**没有**"某个计数器代表某种所有权效果"这回事。要让一个行动改动所有权，改的是那个
行动的向量；要调整平衡，改的也是行动。18 个计数器现在只剩三个用途：

1. 卡牌与顾问的**条件**（"这件事做过几次了""还能不能做"）；
2. 六条路线日志与土地集体化日志的**完成条件**里那些按次数计的部分；
3. 面板上的**流水账**显示（农业五项无上限、其余显示 `n/上限`）。

历史向量的数值并没有丢：它们逐条搬回了各自的选项里（31 个调用点），
其中农业两项（自愿／强制集体化）用的是 5C 校准后的数值。

## 5. 阈值类玩法的重写

### 5.1 经济路线的控制权门槛

新设计提供两个命名判定，替换 `requiresControl(state)`：

```ts
// src/game/rules/economyReforms.ts
export const ECONOMY_ROUTE_RULES = {
  /** 温和工团：工业必须基本脱离私人，且国家必须拿到实权。 */
  syndicalistControl: (state: GameState): boolean => {
    const industry = getControlShares(state).industry;
    return getSocializedShare(state, 'industry') >= 70 && industry.state >= 25;
  },
  /** 自由公社：土地与工业都必须在劳动者手里，国有不算数。 */
  freeCommuneControl: (state: GameState): boolean =>
    getWorkersShare(state, 'land') >= 60 && getWorkersShare(state, 'industry') >= 55,
} as const;
```

**两条路线终于分道扬镳**：

| 路线 | 要求 | 1936·5 开局位置 | 要走多远 |
| --- | --- | --- | --- |
| 温和工团 | 工业社会化 ≥ 70 **且** 国有 ≥ 25 | 社会化 9、国有 5 | 需要大规模国有化（铁路 ×3 → 国有 +18，外资没收 ×3 → +18） |
| 自由公社 | 土地劳动者 ≥ 60 **且** 工业劳动者 ≥ 55 | 土地 6、工业 4 | 需要大规模接管（煤矿、合作社、集体化） |

旧设计里两条路线读同一个 `workerControl > 60`，做完同一套操作就能同时推进。新设计让它们**在饼上分道扬镳**：温和工团要的是国有那块长大，自由公社要的是工会那块长大——而这两块是**互相挤占**的（社会化总量有限，国有多了工会就少）。

进度条相应改写（以温和工团为例）：

```ts
const industry = getControlShares(state).industry;
const controlProgress = Math.min(
  (getSocializedShare(state, 'industry') / 70) * 100,
  (industry.state / 25) * 100,
);
```

### 5.2 五月事件：两道门槛，读工会占比与地方工会所有制

```ts
// 旧：state.cataloniaControl === 'cnt_fai' || state.stats.workerControl >= 60
// 新（用户定稿）：
export const MAY_DAYS_UNION_SHARE_GATE = 30;        // CNT 在工会格局里的占比（组织能力）
export const MAY_DAYS_UNION_OWNERSHIP_GATE = 25;    // 工业饼里的"地方工会所有制"（实际掌握的生产资料）

export const getMayDaysCommitteeControl = (state) => ({
  cntUnionShare: getUnionShare(state).CNT,
  localUnionOwnership: getControlShares(state).industry.union,
  total: cntUnionShare + localUnionOwnership,
});

export const holdsMayDaysCommitteeControl = (state) => (
  cntUnionShare >= MAY_DAYS_UNION_SHARE_GATE && localUnionOwnership >= MAY_DAYS_UNION_OWNERSHIP_GATE
);

export const canBackMayDaysCommittees = (state) => (
  (state.cataloniaControl === 'cnt_fai' || holdsMayDaysCommitteeControl(state))
  && workerWeight(state, 'POUM') + 1e-9 >= 0.4
);
```

**为什么是这两项而不是单一数值**：五月事件打的是巴塞罗那电话局，那既是一场**工会的罢工**（需要会员与组织，读 `unionShare.CNT`），也是一场关于**谁拥有电话公司**的争夺（需要生产资料，读工业饼的 `union` 桶）。只有会员人数而没有所有权，工会能罢工但守不住厂房；只有集体化而没有会员，厂房是空的。

**与旧门槛的对照**：

| 剧本 | CNT 占比 | 地方工会所有制 | 合计 | 门槛 | 是否通过 |
| --- | ---: | ---: | ---: | --- | --- |
| 1931·4 | 10 | 0 | 10 | 30 + 25 | ❌ |
| 1933·11 | 26 | 1 | 27 | 30 + 25 | ❌ |
| 1936·7 | 27 | 1 | 28 | 30 + 25 | ❌ |

**开局两道门都是关着的**：玩家必须真的把工会做大（工会扩张、群众集会、罢工）**并且**把工厂拿到手（煤矿接管、佩罗的工业集体化、加泰罗尼亚防御）。只走其中一条路都不够。

**事件界面必须显示这两项读数**（`may_days.tsx` 的 `renderContent` 已实现）：`CNT 工会占比 27/30、地方工会所有制 1/25`，门槛未达时左边框标红。玩家必须能看见"差在哪一项"，否则会误以为是自己运气不好。

数值留待实测调：反馈"几乎必输"时先调这两个数，别动其他公式。

### 5.3 街头与军事公式

`mitin_popular.ts` 的五个公式读"我们能在街上动员多少人"，一律换成**工业劳动者份额**：

```ts
// 旧：const cntMilitancy = s.stats.anarchistMilitia * 1.2 + s.stats.workerControl * 0.8;
// 新：
```

## 6. 界面

### 6.1 为什么是"饼"而不是"条"

两根条（土地社会化 14%、工业社会化 9%）能表达"多少"，表达不了"**归谁**"——而"归谁"是这套系统的全部意义。六分饼一眼能看出四件事：劳动者那块有多大、国家那块是不是在长、**大庄园/教会是不是在缩**、以及**自耕农/小业主那两块有没有被动**。

最后一条尤其重要：CNT 的土地政策如果动到了自耕农，那 44% 的 `smallholders` 会缩小，而这个后果应当**在图上直接可见**——它对应的是 `Labradores` 支持度的下滑。

### 10.2 与设计的一处重要偏差：逐月一致做不到，也不该做

**原定硬指标**是"同一串选项序列下，新旧 workerControl 逐月差值为 0"。实施时它对不上，原因不是实现错误，而是**两种模型的几何形状不同**：

| | 旧：一根 0—100 的条 | 新：两张所有权饼 |
| --- | --- | --- |
| 写入点的效果 | 无摩擦累加（佩罗 +5、桑蒂利安 +8、土改 +10…） | 受"私人还剩多少"约束的转移 |
| 一次剧本的可涨空间 | 100 | 1931：工业 8 + 土地 10（**受战前上限**） |
| 全部写入点的总承诺 | 约 96 点 | 同上，超出的部分无法落地 |
| 终值（一串固定选项后） | 41 | 约 18—21（取决于剧本） |

也就是说：旧口径下 workerControl 是"运动的控制**能力**"，可以一路涨到 100；新口径下它是"工人**真的拥有**多少生产资料"，1931 年的乡村只有那么多地可动。**这正是这次改造要达成的效果**，所以验收标准改成了三条可证伪的不变量（写在 scripts/test-control-shares.ts 第 5 节）：

1. 派生值严格等于两个部门劳动者份额的均值；
2. 每次影响力写入之后，饼守恒且非负；
3. 实际转移量 ≤ 承诺量，且差额只能用"私人池不足"解释。

**这条偏差需要你知道**：第 5A 期之后，**战前能积累的工人控制远少于旧设计**（1931 约 18—21 的上限均值，而不是 40）。这是有意的——旧设计的"战前封顶 40"是一条日历规则，新设计是"战前乡村只有那么多可转移的地"。**如果你希望战前更宽松，调 §4.2 的上限表，而不是恢复逐月一致的验收标准。**

### 10.3 实施中发现并修正的三个问题

**① 整数化会吃掉按比例的削减。** 月度收拢原本"按各项比例削减社会化桶"，但社会化总量可能只剩 1—2 点，cut × (value / pool) 小于 0.5 就被 Math.round 抹平，于是永远收不到位（测试里表现为"收拢 200 个月仍未到位"）。改成**把削减量记到最大的社会化桶上**，保证每月真的掉 1 点。

**② 五月事件的门槛必须同时改。** canBackMayDaysCommittees 原本读 state.stats.workerControl。workerControl 现在是**派生缓存**，只在 reducer 跑完之后更新；测试夹具手写 controlShares 时缓存还是旧值，于是门槛读到过期数据。这暴露了一条一般性规则：**读出口不能读派生缓存，必须读所有权饼**。门槛因此改为 getWorkersShare(state, 'industry') >= 55，并抽成常量 MAY_DAYS_COMMITTEE_CONTROL_GATE。

**③ 分部门的重心必须写进代码注释。** 15 个写入点里，有明显部门属性的（佩罗 = 城市、土改 = 乡村、群众集会合作社 = 城乡各半）用纯重心（{ land: 0, industry: 1 }），制度性的（国防委员会、民兵合法性、军事化抉择）按 3:7 或 4:6 分。这条规则写在 applyControlInfluence 的文档注释里，避免后来者随手写一个 0.5/0.5。

### 10.6 一次数据事故与恢复（5C 期间，必须先记录）

**发生了什么**：5C 实施过程中，两个**未纳入版本控制**的动作卡文件
（`src/game/action_affairs/military_training.ts`、`militia_legality.ts`）连同它们的
五处登记一起消失：`types.ts` 的两个计时器字段、`scenarios/base.ts` 的初值、
`effectPreview.ts` 的两个标签、`phaseOrchestrator.ts` 的月度递减、
`editor/src/simulator/gameSandbox.ts` 的沙盒初值。触发原因是一段
`git stash push -- <paths>` / `git stash pop`：工作区里这两个文件是**未跟踪**的，
stash 不会带走它们，而后续的检出/清理把它们抹掉了；`git fsck --lost-found`
与全部 stash 里都没有它们的对象（从未 `git add` 过，所以从未成为对象）。

**怎么恢复的**：用最后一次**成功构建**的产物
`dist/assets/index-BPc_IXky.js`（构建时这两个文件还在）。把压缩后的定义逐段还原成
TypeScript，并按当前助手签名（`adjustFactionDissent` / `adjustFactionDissents` /
`adjustMilitarization` / `applyControlInfluence` / `clampLawLevel`）对齐；
两个计时器在**五处**登记点全部补回。

**这次事故教了三件事**（都写在这里，免得下次再踩）：

1. **`git stash` 不能用来暂存未跟踪的实现文件**。要暂存就先 `git add`，
   或者干脆提交。本次全部经济改造与控制度实现都是未跟踪状态，风险一直存在。
2. **构建产物是最后一道备份**。`dist/` 里的 bundle 比源码更长寿，恢复时它是唯一
   的事实来源；因此**在跑任何会覆盖 `dist/` 的构建之前，先把它复制出去**。
3. **恢复之后必须做全库损失审计，而不能只看编译是否通过**。编译通过只说明
   "被引用到的东西没坏"；如果一个文件连同它的登记行一起消失，编译器一无所知。
   本次用的办法是**按 id 对拍**：从 bundle 里抽出全部 514 个内容 id
   （卡牌、事件、日志、法律、组织、成就），与 `src/` 对拍 —— 结果只有难度档位
   （`easy/hard/normal/sandbox/historical`，源码里用双引号所以正则漏掉）与 SVG 滤镜 id
   `wood` 是"只在 bundle 里"，以及本次新增的 4 个土地集体化 id 是"只在源码里"，
   **没有第二个内容定义丢失**。

**同一事故还污染了本文档**：写入时 `\r` `\n` `\f` `\a` `\t` 这类转义把若干词的
首字母吃掉了（`npm`→`pm`、`renderContent`→`enderContent`、
`freeCommuneControl`→`reeCommuneControl`、`agricultural_policy`→`gricultural_policy`、
`transferControlShare`→`ransferControlShare`、`requiresControl`→`equiresControl`），
并留下两个制表符。已按"标识符必须存在于 `src/`"的口径全库扫描并修好
（`scripts/__recovery-*` 为一次性脚本，收尾时删除）。
